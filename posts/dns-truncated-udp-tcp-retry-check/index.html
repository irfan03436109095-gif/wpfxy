DNS 回应标着 TC=1，是机场解析失败吗？用 TCP 复查截断

星航2026-11-13— 次阅读
网络技术

DNS 诊断里看到 TC=1，先别当成“机场 DNS 坏了”。RFC 1035 将 TC 定义为答复被截断的标志；RFC 7766 说明解析器收到截断答复后通常应改用 TCP 取完整结果。问题是这次查询能否完成重查，而非单凭 TC 就给代理线路下结论。

先保留同一查询的条件

记下域名、记录类型、查询的解析器、时间、网络和客户端代理模式。只查询你有权测试的公开域名；内网名称不要随意发给外部解析器。若是抓包或 DNS 工具明确显示 TC，再保存这条请求和对应答复的最小证据，不公开工作域名或内部服务器地址。

示意图：TC 标志提示答复被截断，需看同一解析器的 TCP 重查结果。

在 Windows 用同名同类型作 TCP 对照

PowerShell 的 Resolve-DnsName 支持 -Server、-Type、-DnsOnly 和 -TcpOnly。可先运行 Resolve-DnsName -Name example.com -Type TXT -Server <解析器地址> -DnsOnly，再加 -TcpOnly 重查；把示例域名与解析器换成实际测试对象。两次保持名称、类型和解析器相同，记录返回的答案与错误。

这里的命令只比较传输方式；它本身不保证显示 TC 标志。若默认查询成功，客户端可能已经自动回退；若 TCP 成功而前一次失败，只说明传输路径值得继续查，不足以证明前一次一定因截断而失败。

下一步怎么判断

若工具已确认 TC 且 TCP 重查成功，验证真实网页任务即可。若 TCP 超时，检查同一解析器的 TCP 53 可达性、网络或客户端规则；若 UDP 和 TCP 都失败，先查域名和解析器状态。RFC 9210 也要求 DNS 服务支持 TCP 查询，不能把 TCP 只视为区域传送专用。验收以相同条件下得到完整答复并能完成实际任务为准。

资料来源

RFC 1035：DNS 传输与 TC 标志；RFC 7766：DNS over TCP；Microsoft：Resolve-DnsName。核验日期：2026-11-13（北京时间）。
